# Java 团队 MCP 服务改造需求清单

> 版本：v1.0 | 日期：2026-07-21
> 背景：机场智能客服（Parlant + MCP）重新开发。现有航班查询 / POI / 失物招领 MCP 服务由小程序后端 API 直接包装而来，存在 UI 导向、用户上下文缺失、错误语义不适配 Agent 三个错位（详见《MCP服务改进与设计方案.md》）。
> 本文档是 AI 侧对 Java 团队的**正式输入清单**，按"必须提供 / 需要配合 / 无需负责"分类。每项附验收标准。

---

## 一、必须提供（阻塞项，缺则无法开工）

### 1. 业务语义包（第 1 周）

| 项 | 内容 | 验收标准 |
|---|---|---|
| 1.1 现有接口全量清单 | 小程序后端涉及航班、POI、失物招领、订单、退改签的全部 REST 端点、字段字典、业务码表 | 每个字段有中文含义；每个业务码有解释 |
| 1.2 业务规则说明 | 航班状态枚举语义（如"计划/延误/取消/备降"）、退改签规则、失物招领流转状态 | AI 侧能据此判断哪些字段是旅客关心的 |
| 1.3 任务场景映射 | 从旅客问题到接口的映射（如"我的航班登机口"→ 订单+航班动态两个接口） | 覆盖 FR-401~403 列出的全部场景 |

### 2. 按任务重组的工具契约（第 2-3 周）

原则：**不再 1:1 映射 REST 端点，按旅客任务定义工具。**

| 项 | 要求 | 验收标准 |
|---|---|---|
| 2.1 端点合并 | `flight_query` 单工具内部聚合 search+detail；detail 故障由服务端自行降级 search 并标注 `data_source: "search_fallback"` | Agent 侧一次调用获得完整答案（状态/登机口/行李转盘/值机柜台） |
| 2.2 字段瘦身 | 剔除 UI 专用字段（图片 URL、样式、banner、分享文案）；按旅客关注度排序字段 | 单次响应体 ≤ 8KB；无渲染专用字段 |
| 2.3 参数语义化 | 城市/机场接受三字码+中文名容错（"浦东"→PVG）；日期支持 `today`/`tomorrow`/具体日期 | 每个参数有中文 description + 示例值（供 LLM 理解） |
| 2.4 Schema 合规 | enum 仅用 string；不用深层 `anyOf`；object 参数拍平或嵌套 ≤2 层；`$ref` 仅本地 | 通过 AI 侧提供的 schema 校验脚本（避免 parlant 类型映射降级） |

### 3. 语义标注与执行安全

| 项 | 要求 | 验收标准 |
|---|---|---|
| 3.1 MCP annotations | 只读工具（航班/POI/失物查询）标 `readOnlyHint: true`；执行类（退改签、失物登记）标 `destructiveHint: true` | 每个工具携带 annotations |
| 3.2 幂等键 | 所有执行类工具接受 `idempotency_key` 参数，服务端保证同键不重复生效 | 同 key 重复调用返回首次结果，不产生二次扣款/二次提交 |
| 3.3 确认前置 | 执行类工具拆为"试算/预检"（只读，返回费用与影响）+"确认执行"两步 | 不存在单步直接生效的执行类工具 |

### 4. 旅客身份方案（订单/退改签的前置）

| 项 | 要求 | 说明 |
|---|---|---|
| 4.1 身份传递机制 | 工具入参显式携带旅客标识（手机号+验证码 / 证件号+姓名），不依赖小程序 session/OAuth CC | OAuth CC 只是服务间认证，不能替代用户身份 |
| 4.2 隐私合规说明 | 证件号等敏感字段的传输/日志脱敏方案 | 日志中敏感字段必须掩码；符合零出域要求 |
| 4.3 权限边界 | 一个身份只能查/改本人订单的服务端校验 | 越权请求返回明确错误码 |

### 5. 统一错误模型

所有工具错误返回统一结构（替代 HTTP 码+业务码直抛）：

```json
{
  "code": "FLIGHT_NOT_FOUND",
  "retryable": false,
  "degraded": false,
  "user_message": "未查到该航班，请确认航班号和日期",
  "canned_response_fields": { "reason": "flight_not_found" }
}
```

- `retryable`：AI 侧据此决定是否自动重试；
- `degraded`：数据来自降级路径（如 detail 故障走 search 兜底）时置 true；
- `user_message`：业务侧产出的对旅客口径（业务最懂该怎么说）；
- 验收：错误码全量清单 + 每个码的三要素（可否重试/可否降级/口径文案）。

### 6. 认证与网络

| 项 | 要求 |
|---|---|
| 6.1 凭据签发 | OAuth client-credentials / HMAC 密钥的正式签发流程（非 PoC 临时凭据），含轮换周期与轮换接口 |
| 6.2 网络路径 | 生产零出域：服务暴露在内网可达地址；如必须出域（腾讯云航班 MCP），提供专线/出口白名单方案 |
| 6.3 限流配额 | 每凭据的 QPS 配额与超限行为（429 + Retry-After） |

## 二、需要配合（联调与运维期）

| 项 | 内容 | 时间 |
|---|---|---|
| 7.1 测试环境 | staging 端点 + 测试数据（覆盖正常/延误/取消/无结果/上游故障五类场景）+ 测试旅客账号 | W3 |
| 7.2 上游 detail 修复 | 航班 detail 接口故障的修复计划与时间点（目前网关用 search 兜底，修复后下线兜底逻辑） | 尽快 |
| 7.3 SLA 承诺 | p95 延迟、可用性目标、超时建议值（AI 侧据此设网关超时/熔断阈值） | W3 |
| 7.4 变更治理 | 工具 schema 变更提前通知（≥5 工作日）；版本化策略（工具名或 metadata 带版本，新旧并行期 ≥2 周） | 持续 |
| 7.5 健康端点 | 每服务 `/health`（含依赖自检与版本号），供网关健康聚合 | W4 |
| 7.6 故障接口人 | 值班联系方式 + 故障升级路径（熔断打开时 AI 侧告警给谁） | 上线前 |

## 三、无需 Java 团队负责（AI 侧边界）

以下由 AI 侧在网关/Parlant 层自行解决，避免职责混淆：

- 熔断器、重试策略、双实例网关部署；
- MCP → parlant 类型映射、工具注册、guideline 绑定；
- 降级时的话术组装与转人工触发（Java 只提供 `user_message` 素材）；
- 调用成功率/延迟指标采集与看板；
- LLM 提示词与缺参反问逻辑。

## 四、交付时间线（对齐 PRD 里程碑）

| 周 | Java 交付 | AI 侧动作 |
|---|---|---|
| W1 | §1 业务语义包 | 输出 schema 校验脚本与契约示例 |
| W2 | §2 工具契约草案评审 | 契约评审，反馈修订 |
| W3 | §3/§4/§5/§6 实现 + §7.1 测试环境 | 网关适配层开发 |
| W4 | §7.5 健康端点；联调 | 端到端联调 + 混沌演练 |
| W5+ | §7.2 detail 修复、§7.3 SLA 确认 | 成功率验收（≥98%） |

> 风险：若 W2 契约评审发现 Java 侧无法在短期内完成端点合并（§2.1），AI 侧将在网关层长期承担聚合逻辑——可行但违反"薄封装"原则，需在评审时明确。
