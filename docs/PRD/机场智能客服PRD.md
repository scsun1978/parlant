## 1. 背景与目标

### 1.1 背景

机场客服当前面临：高峰时段人工坐席溢出、政策类问题（退改签/行李/安检）口径不统一、服务留痕与民航合规审计要求严格。拟建设基于 LLM 的智能客服，覆盖小程序文字通道，并为数字人语音通道预留能力。

前期技术研究表明：**客服场景的核心矛盾不是"agent 不够聪明"，而是"话术不可控"**。因此选型从通用编排框架（LangGraph/liteflow-react-agent 类）转向"行为约束型 harness"（Parlant），辅以 Hybrid RAG 知识底座与 MCP 工具生态。

### 1.2 产品目标

**总体目标**：在小程序文字通道上线"话术可控、事实可溯、审计可回放"的 AI 客服，承接高频咨询场景的人工首接，让人工坐席聚焦复杂与投诉类问题。

**北极星指标**：人工接管率（衡量"AI 能否独立闭环"，决定分流价值）与高合规问答事实准确率（衡量"敢不敢让 AI 说"，一票否决项）。

#### 1.2.1 目标指标与衡量口径

| 目标 | 衡量指标 | 目标值 | 衡量口径 / 数据来源 |
|---|---|---|---|
| 分流人工压力 | 人工接管率 | ≤ 15% | 转人工会话数 ÷ 总会话数，周维度统计（会话中心）；无法解决且未正确转人工的会话视为失败并计入 bad case |
| 回答准确合规 | 高合规问答（退改签/行李/安检）事实错误 | **零容忍** | 红线场景全量与政策原文/工具返回逐条比对；发现 1 例即触发告警、修复与回归 |
| | 一般问答幻觉率 | ≤ 2% | 每周随机抽样 ≥100 条人工标注（质检工作台） |
| 体验流畅 | 文字通道首 token 延迟 | ≤ 1.5 s（p95） | 全链路 trace 数据，p50/p95 双口径监控 |
| | 意图覆盖率（Top 50 高频意图） | ≥ 85% | 正确路由且回答正确；评测集（≥500 条）+ 线上抽样双重验证 |
| 合规可审计 | 全链路 trace 可回放 | 100% | 审计中心随机调取任意会话任意一轮，决策链可完整回放 |
| 成本可控 | 单次会话成本 | ≤ ¥0.05（实测后调整） | （模型 token + 检索 + 工具调用）成本 ÷ 会话数，W5 压测实测后锁定基线 |
| 工具可靠 | 工具调用成功率 | ≥ 98% | MCP 工具成功调用 ÷ 总调用，周维度；跌破即告警（FR-406） |

#### 1.2.2 分阶段目标

| 阶段 | 周期 | 核心目标 | 达标要求 |
|---|---|---|---|
| PoC 验证期 | W1–W6 | 验证"话术可控"成立，完成选型终审 | 第 7.1 节验收门槛全部达标；bake-off 六项不劣于基线框架 |
| 试点灰度期 | W7–W10 | 小流量真实旅客验证，跑通运营闭环 | 高合规零错误；人工接管率 ≤ 20% 且逐周向 15% 收敛（建议值，灰度首月可评审调整）；bad case 修复闭环机制实际运转 |
| 全量运营期 | W11–W14 | 全量切流，达成全部产品目标 | 1.2.1 全部指标连续 2 周稳定达标 |
| 二期（另行立项） | W15 起 | 数字人语音通道、英文服务、知识图谱（按 W6 判定结论） | 见各专项方案，语音门槛见 PoC 清单第六节 |

> 阶段目标未达成即不进入下一阶段；指标口径的变更需经合规与运营双方评审并留痕。

### 1.3 范围

**本期包含**：小程序文字客服（航班查询、退改签引导、行李规则、安检须知、失物招领、投诉与转人工）、知识库运营后台、合规话术管理、审计留痕。

**本期不包含**：数字人语音通道（仅做架构预留，验证标准见 PoC 清单第六节）、机票销售交易闭环、多语言服务（中文优先，英文二期）。

## 2. 用户与核心场景

### 2.1 用户角色

| 角色 | 诉求 |
|---|---|
| 旅客（C 端） | 快速获得准确、口径统一的答复；复杂问题能顺畅转人工 |
| 客服运营（B 端） | 无需开发即可维护话术与规则；能看到 bad case 并修复 |
| 合规/审计 | 任意一条回复可回溯其依据（知识来源、命中规则） |
| 坐席班长 | 接管会话、查看 AI 对话上下文、必要时代发 |

### 2.2 核心场景（User Story）

**S1 航班查询**：旅客问"明天 MU5101 几点起飞/哪个航站楼"→ AI 调用航班工具实时查询并回复；缺少航班号时自然反问。
**S2 退改签引导**：旅客说"我要退票"→ AI 进入多步引导（确认订单→告知规则→计算费用→确认执行），规则表述必须与政策原文一致。
**S3 政策问答**："充电宝能带上飞机吗"→ AI 命中知识库原文回答，答案附依据，不自由发挥。
**S4 延误服务**："航班延误了有赔偿吗"→ AI 按延误政策 guideline 应答（先安抚、再给政策口径），不得承诺具体赔偿金额（红线）。
**S5 失物招领**：多步流程登记（物品描述→遗失地点→联系方式），进度可跨会话恢复。
**S6 投诉与转人工**：识别投诉意图或旅客明确要求人工 → 平滑转接，人工接管期间 AI 静默，坐席可见完整对话上下文。
**S7 非线性对话**：对话中旅客插话、跳话题、反悔（"算了不退了，改签到后天"）→ AI 正确跟随最新意图。

## 3. 总体架构

```
┌─────────────┐   ┌──────────────────────────────────────────┐
│ 渠道层       │   │ Java 业务后端（既有系统）                  │
│ 小程序/H5    │◄──┤ 会话/客户体系映射 · 鉴权 · 渠道适配 · 转人工工单 │
└─────────────┘   └──────────┬───────────────────────────────┘
                             │ REST / 事件流
                  ┌──────────▼───────────────┐
                  │ Parlant 服务（Python）     │
                  │ Guideline 匹配与仲裁       │
                  │ Revision 事实溯源          │
                  │ Canned Response 话术控制    │
                  │ Journey 多步引导           │
                  └──┬─────────┬─────────┬───┘
            REST/Hook│         │MCP      │REST
        ┌────────────▼─┐ ┌─────▼──────┐ ┌▼──────────────┐
        │ RAG 微服务     │ │ MCP 工具群  │ │ MongoDB        │
        │ Hybrid 检索    │ │ 航班查询    │ │ 会话/事件/规则  │
        │ BM25+向量+RRF │ │ 订单/退改签 │ │ 持久化          │
        │ +Rerank       │ │ 失物招领等  │ └────────────────┘
        └──────┬───────┘ └────────────┘
               │
        ┌──────▼───────┐        ┌────────────────┐
        │ 知识库文档     │        │ LLM 推理底座     │
        │ ES + 向量库   │        │ 自托管模型（线0） │
        └──────────────┘        │ OpenAI 兼容 API │
                                └────────────────┘
```

**关键架构决策**：

1. **Parlant 独立部署为 Python 服务**（MongoDB 持久化），Java 后端经 REST/事件流集成——Parlant 无 Java SDK，此为官方推荐拓扑。
2. **RAG 做成独立微服务**：Parlant 侧仅实现 `retriever` 钩子函数做一次 HTTP 调用；检索基础设施（ES BM25 + 向量库 + RRF 融合 + Rerank）自运维。
3. **业务工具经 MCP 暴露**：航班查询、订单、退改签等既有 Java 接口包装为 MCP server，Parlant 内置 fastmcp 客户端接入，获得"条件式工具供给 + 缺参反问"能力。
4. **模型层沿用 PoC 清单"线 0"**：自托管模型（GLM/DeepSeek/Qwen 候选）暴露 OpenAI 兼容 API，Parlant 经 LiteLLM/OpenAI 适配器接入。

## 4. 功能需求

### 4.1 对话引擎与规则治理（P0）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-101 | Guideline 规则管理 | 以"当 X 则 Y"自然语言维护客服 SOP（如"当客户询问延误赔偿时，先安抚，然后告知延误险政策入口"）；支持关键级（高/中/低）、优先级、依赖关系 |
| FR-102 | 规则冲突检测 | 新增规则时自动与存量规则做 coherence check，冲突规则需人工确认后入库 |
| FR-103 | 红线机制 | 支持"绝不允许"类规则（如不得承诺赔偿金额、不得评价竞争对手航司）；红线场景叠加输出过滤双保险 |
| FR-104 | 歧义消解 | 旅客表述模糊时（如"改签"未指明日期），AI 先澄清再行动 |
| FR-105 | 已应答抑制 | 同一会话内已执行过的安抚/致歉类话术不重复出现 |
| FR-106 | 术语统一 | 通过 Glossary 机制保证"超售""非自愿降舱""经停"等术语口径全渠道一致 |

### 4.2 话术合规控制（P0）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-201 | 话术模板库 | 高合规场景（退改签费用、行李限额、安检违禁品、延误政策）全部使用预审批话术模板，支持 `{{航班号}}` `{{费用}}` 等字段渲染 |
| FR-202 | 严格模式 | 高合规场景启用 CANNED_STRICT：回复只能选自模板，选不到发兜底话术并记录告警 |
| FR-203 | 动态知识槽位 | 政策模板预留知识字段，由 RAG 检索结果经模板渲染注入（COMPOSITED 模式），兼顾话术合规与知识时效 |
| FR-204 | 事实溯源 | 回复中的每条事实必须能溯源到工具返回或知识库原文，无法溯源的内容不得输出（引擎 revision 机制保障） |
| FR-205 | 话术版本治理 | 模板修改留痕、可回滚；模板与知识库版本关联，支持按时间回溯"当日回复依据" |

## 6. 关键技术方案

### 6.1 智能内核：Parlant（行为约束 harness）

- Guideline 声明式规则 + 每轮全量重匹配，天然适应非线性对话
- 生成后 revision 循环强制事实溯源，防幻觉为结构性能力
- CANNED_STRICT/COMPOSITED 话术模板，高合规场景输出物理可控
- Journey 自适应多步流程（可跳步/回溯/恢复）
- **已知风险**：项目年轻（3.3.1，API 变动快）；单进程架构，多副本部署方案需 POC 验证；每轮多次 LLM 调用推高延迟与成本

### 6.2 Hybrid RAG（独立微服务）

- 检索：ES（BM25 + jieba 分词）+ 向量库 + RRF + Rerank 模型
- 注入：Parlant retriever 钩子，结果仅存活当轮
- **红线**：高合规问题的答案必须命中知识库原文，检索为空时不得生成、转模板兜底口径

### 6.3 MCP 工具生态

- 既有 Java 业务接口包装为 MCP server；Parlant fastmcp 客户端接入
- 注意 fastmcp 版本锁定与复杂 schema 类型映射验证（POC 项）

### 6.4 知识图谱（分阶段，默认不在本期）

| 阶段 | 动作 | 判定标准 |
|---|---|---|
| 1 | Hybrid RAG + MCP 上线 | 基线准确率 |
| 2 | bad case 归因，统计"多跳/关系型"失败占比 | **<10% 不建 KG**，用结构化表 + metadata 过滤补 |
| 3 | 占比高 → 轻量方案（航司-航站楼、舱位规则结构化表） | 多数两表关联可解 |
| 4 | 确有复杂多跳需求 → Neo4j / GraphRAG | 明确 ROI 后投入 |

**边界**：实时/交易数据（航班动态、余票）不进 KG，只走 MCP 工具；KG 只承载慢变领域知识（设施布局、政策条款结构、流程依赖）。

### 6.5 模型层

沿用 PoC 清单"线 0"：自托管 2 个候选模型（GLM / DeepSeek / Qwen 系），OpenAI 兼容 API；POC 期间同时验证商用 API 作为对照与兜底。

## 7. 评测与验收

### 7.1 验收门槛（与 PoC 清单对齐）

| 指标 | 门槛 |
|---|---|
| 意图覆盖率（Top 50） | ≥ 85% |
| 高合规问答事实错误 | 零容忍 |
| 一般问答幻觉率 | ≤ 2% |
| 工具调用成功率 | ≥ 98% |
| 人工接管率 | ≤ 15% |
| 首 token 延迟 | ≤ 1.5 s |
| 全链路 trace 可回放 | 100% |

### 7.2 Harness 对比 bake-off（选型终审用）

同一自托管模型为控制变量，Parlant vs 备选框架（AgentScope / LangGraph 基线）对比六项：

1. 意图识别准确率（100 条真实问法，含口语/错字/中英混杂）
2. 多跳任务完成率（"查航班并改签"类组合请求）
3. 话题切换恢复率（插话/反悔/跳题）
4. 事实准确率（与工具/知识库原文逐条比对）
5. 规则合规率（植入红线的违规次数）
6. 单轮延迟与 token 成本

评测语料 ≥500 条真实/仿真问句，含 20% 长尾与对抗样本（方言、错字、多意图混句、诱导性提问）；其中专设 **10–15 条多跳关系型问题**（航站楼关联/舱位规则/设施从属），作为是否引入知识图谱的量化判定依据。

## 9. 风险与依赖

| 风险 | 等级 | 缓解 |
|---|---|---|
| Parlant 项目年轻、API 变动频繁 | 高 | 锁定版本；核心定制收敛在 guideline/retriever/工具层，减少框架侵入 |
| 中文匹配准确率不达标 | 高 | W1–2 优先实测；备选方案为 guideline 中英双语书写或回落 AgentScope 线 |
| 多轮 LLM 调用推高延迟/成本 | 中 | 压测后调优批大小与低关键级规则频率；语音通道延迟目标单独评估 |
| 单进程架构的水平扩展 | 中 | POC 验证多副本 + 会话亲和性；必要时前置路由按 conversationId 粘性分发 |
| Hybrid RAG 基础设施自建工作量 | 中 | 评估 RAGFlow 等现成产品替代自建；检索服务化隔离风险 |
| MCP/fastmcp 生态变动 | 低 | 版本锁定；MCP 工具层薄封装，可整体替换 |
| 民航合规评审 | 高 | 审计留痕（FR-701/702）与数据私有化作为 W7 前必须完成的硬门槛 |
| Parlant 默认向量库为内存瞬态实现（TransientVectorDatabase），glossary 术语重启后丢失（PoC 实测确认；话术/Journey 持久化不受影响，embedding 有本地缓存） | 中 | 重启后重跑种子脚本（幂等、秒级）；生产前切换持久化向量库（Chroma/Qdrant）并纳入 W7 硬门槛评估 |
| DeepSeek 结构化输出偶发非法 JSON，引擎重试耗尽后该轮"已读不回"（多轮专项实测 7/36≈19%，日志定位 deepseek_service 解析失败） | 高 | 生成失败重试 + 兜底话术（安全回复）作为上线前必修；上线评审以连续 100 轮零"已读不回"为门槛 |
| Parlant 引擎串行调用结构推高延迟（实测 preamble 4.5s、完整答复 15–37s、结构底线 8–15s；流式无益） | 高 | 规则降频/匹配层模型分级压缩调用次数；文字通道接受 preamble+渐进答复形态；语音通道不走 Parlant（数字人走 hermes 线，见 ADR-0001） |
