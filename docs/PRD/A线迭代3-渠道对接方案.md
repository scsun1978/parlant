## 1. 定位：为什么必须有 Java BFF

当前旅客流量是"测试客户端直连 Parlant REST"。上真实小程序渠道前必须插入业务后端，因为 Parlant 侧有四个硬性缺口：

| 缺口 | 后果 | Java BFF 的职责 |
|---|---|---|
| Parlant 是 development auth（全通无鉴权） | 任何人可调引擎、看他人会话 | **鉴权与租户隔离**：微信小程序登录态 → 渠道 token → 仅可访问本会话 |
| 无用户/会话体系 | 无法关联 openid 与会话连续性（FR-603） | **会话/客户体系映射**：openid ↔ customer/session，断点续聊 |
| 渠道协议不匹配 | 小程序消息模型 ≠ Parlant 事件流（preamble/多段/工具事件） | **渠道适配**：引擎事件流 → 小程序友好的消息模型 |
| 兜底话术位置已定（ADR 口径：不落引擎） | 引擎超时/失败/已读不回时旅客无响应 | **渠道层兜底**：超时/异常检测 → 安全话术 + 转人工入口 |

> 与 admin-bff 的分工：**Java BFF 面向旅客（渠道，要求高可用）**；admin-bff（FastAPI）面向运营（后台）。两者独立服务、独立伸缩；admin-bff 后续可置换进 Java（接口契约不变），本方案不动它。

## 2. 职责清单（六项）

1. **鉴权与会话映射**：`wx.login` code → code2session 换 openid/unionid → 签发渠道 token（JWT，2h）；映射机场会员/旅客 ID（FR-603：同一旅客跨会话保持上下文）
2. **消息通道**：小程序消息收发、事件流裁剪（preamble 可显式标注、tool 事件折成"正在查询…"状态条、多段答复合并或顺序推送）
3. **兜底话术层**：三类触发——引擎 error（含已读不回，引擎已有 fallback 消息时透传）、渠道超时（>Ns 无 ready/completed）、上游不可用；话术文案走管理后台审批流治理
4. **转人工工单**：触发收集（旅客要求/投诉意图/连续 2 次未解决/红线）→ 工单创建与分配（对接既有客服系统/坐席工作台）→ session manual 接管/恢复；忙时溢出（FR-604：告知等待+留存问题+回访工单）
5. **合规与安全**：内容审核（注入攻击/不当内容，FR-704）、PII 脱敏（证件/手机号/姓名）、审计日志（全量留痕，对接审计中心）
6. **观测**：渠道侧 SLI（首响应/完成率/兜底率/转人工率）输出到数据看板

## 3. 接口设计

### 3.1 旅客侧（小程序 ↔ Java BFF）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/channel/wechat/login` | POST | `{code}` → `{channelToken, openid 摘要, resumeSessionId?}` |
| `/channel/messages` | POST | `{text}` → 同步返回 `{sessionId, preamble{ text, displayAs:"placeholder" }}`（preamble 秒回，先给旅客反馈） |
| `/channel/messages/stream` | **WebSocket**（`wx.connectSocket`） | 订阅本会话事件：`tool_start("正在为您查询航班…")` / `message_append(段)` / `message_done` / `fallback` / `handoff_offered`；WS 不可达时降级 `GET /channel/messages/poll?afterOffset=` 增量轮询（1.5s 间隔） |
| `/channel/history` | GET | 分页拉取本会话历史（断线恢复/重进小程序续聊） |
| `/channel/handoff/request` | POST | 旅客主动转人工 → 返回受理结果（排队位置或溢出话术+回访工单号） |

**协议决策**：小程序 `wx.request` 不支持 SSE 且 60s 超时，而引擎完整答复 15–40s——**同步请求只覆盖 preamble；正式答复经 WebSocket（`wx.connectSocket`）或降级增量轮询推送**。这是渠道适配的核心决策（备选"长轮询 25s+续拉"被否：会放大引擎连接占用）。

### 3.2 坐席侧（客服系统/坐席工作台 ↔ Java BFF）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/handoff/queue` | GET | 转人工队列（按触发原因分类：旅客要求/投诉/连续未解决/红线） |
| `/handoff/{ticketId}/take` | POST | 坐席接单 → BFF 将 session 置 manual、推送完整 AI 对话上下文+已执行动作 |
| `/handoff/{ticketId}/messages` | WS | 坐席实时收发（BFF 桥接 session 事件流） |
| `/handoff/{ticketId}/release` | POST | 结束接管 → session 恢复 auto、生成小结入工单 |
| `/handoff/overflow` | POST（内部） | 全忙溢出：生成回访工单（旅客问题+联系方式） |

### 3.3 内部（Java BFF ↔ Parlant / admin-bff）

- Java BFF → Parlant：REST（sessions/events，development auth 仅限内网）+ 事件流长轮询订阅（活跃会话按 conversationId 粘性路由到对应 BFF 副本）
- Java BFF → admin-bff：兜底话术内容治理（admin 审批流）、审计数据归集、可靠性指标（已读不回率/兜底率）回传

## 4. 数据模型（Mongo，与治理库同集群）

| 集合 | 关键字段 | 说明 |
|---|---|---|
| `channel_users` | openid/unionid、会员 ID、脱敏 PII、创建/最近活跃 | 不存明文敏感字段 |
| `channel_sessions` | user_id、parlant_session_id、mode、status、last_active、bff_instance | 会话映射与粘性路由 |
| `handoff_tickets` | session_id、reason_code、status（queued/taken/released/overflow）、agent、timeline | 转人工与溢出回访 |
| `fallback_events` | session_id、trigger（engine_error/timeout/upstream_down）、话术版本、ts | 兜底观测（目标 <2%） |
| `channel_audit` | actor、action、session、payload_hash、ts | append-only，审计中心取数 |

## 5. 关键流程

### 5.1 旅客消息全链路

```
小程序 → wx.login → code2session → 渠道 token
  → POST /messages（幂等键 client_msg_id 防重发）
    → BFF 查/建会话映射 → Parlant POST event(customer)
    → 等 preamble（≤8s）→ 同步返回 preamble + 升级 WS
    → WS 推送：tool_start / message_append×N / message_done
    异常分支：
      · 引擎 error + 引擎 fallback 消息 → 透传 fallback（标注"系统忙，已为您转人工"入口）
      · 45s 无 ready/completed → 渠道兜底话术（走审批文案）+ fallback_events 记录
      · Parlant 不可达 → 降级话术（关键词 FAQ 或人工入口，PRD 可用性降级方案）
```

### 5.2 转人工全链路

```
触发（旅客要求/投诉/连续未解决/红线）→ 建工单（含触发快照）
  → 坐席队列（全忙→溢出话术+回访工单 FR-604）
  → 坐席 take：session PATCH manual → 坐席视图（完整上下文+已执行动作+命中规则）
  → 坐席代聊（human_agent 消息，AI 静默）
  → release：session PATCH auto → 工单小结 → 该会话计入"转人工复盘"（质检工作台发现入口，已打通）
```

### 5.3 灰度切流

渠道按 openid 哈希灰度（5%→30%→100%），与发布管理共用配置；灰度期指标门槛：兜底率 <2%、首响应 p95 ≤8s、转人工率 ≤15%（PRD 目标值）。

## 6. 技术方案

| 项 | 决策 | 理由 |
|---|---|---|
| 框架 | Spring Boot 3 + WebFlux（响应式，天然适配 WS/长轮询） | 团队 Java 主线；事件流场景比 MVC 省线程 |
| 消息推送 | WebSocket 主 + 增量轮询备 | 小程序 wx.request 无 SSE；ws 保活靠 ping（30s）+ 断线重连拉 history |
| 幂等 | `client_msg_id + user_id` 唯一约束，5 分钟窗口去重 | 小程序重发/双击常见 |
| 超时预算 | preamble 8s / 完成 45s / 工具 30s | 对齐引擎实测（preamble 4.5s、答复 15–40s） |
| 粘性路由 | conversationId 一致性哈希（多副本） | Parlant 会话亲和（PRD 风险表） |
| 内容安全 | 前置审核（注入/不当词）+ 后置抽检 | FR-704 |
| 部署 | 生产应用区 ×2，与 Parlant 同区；dev03 先单点验证 | 生产网方案 |

## 7. 里程碑与验收（迭代 3 范围内）

| 周 | 内容 | 验收 |
|---|---|---|
| W1 | 登录/会话映射/消息通道（preamble+WS 推送） | 小程序沙盒端到端：发消息收到 preamble+完整答复；断线重连续聊 |
| W2 | 兜底话术层 + 幂等 + 内容审核 | 异常注入（杀引擎/拔模型/超时）旅客均收到安全回复；重发不产生双答 |
| W3 | 转人工工单 + 坐席侧桥接 + 溢出 | 四类触发正确建单；接管 AI 静默、坐席可见完整上下文；全忙溢出出回访工单 |
| W4 | 审计归集 + 灰度开关 + 压测复核 | 证据链可导出；5% 灰度观察指标达标（兜底率<2%、转人工率≤15%） |

**灰度评审门槛**（迭代计划既定）：连续 100 轮零"已读不回"（含兜底覆盖率 100%）+ 答复 p50 ≤15s + 重启数据全存活 + 520 压测全指标 + 审计证据链可导出。

## 8. 工作量与依赖

- 工作量：Java 1 人 × 4 周（W1–W4），前端（小程序）0.5 人 × 2 周（消息区改造+WS），测试 0.5 人 × 2 周
- 外部依赖：小程序 appid/secret 与既有会员体系接口（W1 前）；坐席工作台接口协议（W3 前）；内容审核服务选型（W2 前）
- 风险：① 小程序 WS 保活不稳（降级轮询兜底已设计）；② 引擎延迟对渠道超时的挤压（迭代 2 匹配层分级若未完成，45s 预算需复核）；③ 坐席系统对接排期不可控（先用 admin-bff 会话中心的接管界面顶着，工单 API 先行）
